# Spec: AI-Native Cloud Observability Agent — Coordinator Engine & Agent Layer

**Status:** `ready-for-agent`
**Phase:** 2 — Orchestration
**Spec version:** 1.0

---

## Problem Statement

The domain model (Phase 1) defines the entities and state machines for incident investigation — the Incident aggregate, Hypothesis tree, Evidence, and Remediation. But the model is passive: it has no mechanism to drive an investigation. An SRE doesn't want to manually call `incident.add_hypothesis()` and `hypothesis.confirm()` — they want the system to autonomously gather telemetry, form hypotheses, evaluate them, and produce an RCA.

The gap is an **orchestration layer** that sits above the domain model: a Coordinator that reads the Incident state, calls LLMs and observability tools, applies the results to the domain model, and drives the Incident through its lifecycle from `open` to `resolved`.

## Solution

A **Coordinator engine** that implements a rule-based investigation workflow with LLM-filled content. The Coordinator is the sole driver of the Incident state machine. It follows a deterministic sequence — explore, hypothesize, evaluate, deepen, produce RCA — but the *content* at each step (hypothesis statements, evidence queries, confidence scores, RCA narrative) is generated by an LLM.

Six specialized agents (Metrics, Logs, Trace, Kubernetes, Deployment, Knowledge) are typed function interfaces that the Coordinator calls to gather evidence. Each agent is a 1:1 mapping to an observability source. MCP is hidden behind the agent interface — the Coordinator never touches MCP directly.

The entire orchestration layer is mock-testable: the LLM provider, agent functions, and repository are all injected as dependencies and can be replaced with mocks that return pre-built objects.

## User Stories

1. As an **SRE**, I want the Coordinator to automatically gather exploratory telemetry from all six observability sources when an investigation begins, so that hypothesis generation is grounded in data.
2. As an **SRE**, I want the Coordinator to call an LLM to propose root-cause hypotheses based on exploratory evidence, so that the investigation follows a structured causal reasoning process.
3. As an **SRE**, I want the Coordinator to gather targeted evidence for each hypothesis from the most relevant observability source, so that each theory is validated or refuted with data.
4. As an **SRE**, I want the Coordinator to batch-evaluate all unresolved hypotheses in a single LLM call, so that the LLM can compare hypotheses against each other.
5. As an **SRE**, I want the Coordinator to prune refuted branches of the hypothesis tree, so that investigation effort is focused on the most promising causal paths.
6. As an **SRE**, I want the Coordinator to deepen confirmed hypotheses by generating child hypotheses that drill into the specific mechanism, so that the investigation reaches the root cause.
7. As an **SRE**, I want the Coordinator to only deepen leaf hypotheses (those without children), so that already-deepened branches are not re-processed.
8. As an **SRE**, I want the investigation to converge when no new child hypotheses can be generated or when max depth is reached, so that the investigation terminates in a bounded number of steps.
9. As an **SRE**, I want the Coordinator to produce an RCA with a confidence score and a recommended remediation action, so that I have an actionable output from the investigation.
10. As an **SRE**, I want the Coordinator to produce an RCA even when no hypotheses are confirmed, so that the investigation always reaches a terminal state.
11. As an **SRE**, I want the Coordinator to save the Incident after each step, so that a crash mid-investigation doesn't lose all progress.
12. As an **SRE**, I want the investigation to continue gracefully when an observability source is unavailable, so that a single MCP outage doesn't block the entire investigation.
13. As an **SRE**, I want failed agent calls to produce error Evidence that the LLM can see and reason about, so that the RCA reflects data gaps rather than silently ignoring them.
14. As a **developer**, I want each agent to be a typed function interface (callable), so that I can swap implementations without changing the Coordinator.
15. As a **developer**, I want the LLM provider to be a single-method interface (`generate_structured`), so that I can swap between OpenAI, Claude, DeepSeek, or a mock without changing the Coordinator.
16. As a **developer**, I want the Incident repository to be abstracted behind a protocol, so that I can use an in-memory store for tests and a database for production.
17. As a **developer**, I want a `MockLLMProvider` that returns pre-registered Pydantic objects by schema type (with queued responses for multiple calls), so that I can test the Coordinator without real LLM calls.
18. As a **developer**, I want a `MockAgent` that returns pre-built Evidence objects and applies the `hypothesis_id` from the call, so that I can test agent routing without real MCP servers.
19. As a **developer**, I want the Coordinator to support progressive context selection — each LLM call gets only the fields it needs, never raw telemetry payloads — so that prompts stay within token limits.
20. As a **developer**, I want the hypothesis evaluation to fall back to position-based matching when the LLM returns non-matching hypothesis IDs, so that mock tests work without knowing auto-generated UUIDs.

## Implementation Decisions

### Architecture: Rule-Based State Machine with LLM-Filled Content

The Coordinator follows a deterministic investigation workflow. The LLM is called for content generation (hypothesis statements, evidence queries, confidence scores, RCA narrative), but the *structure* of the workflow — which step comes next — is hardcoded. This is predictable, debuggable, and cheaper than LLM-driven orchestration.

### Investigation Workflow Phases

The `run()` method executes these phases in sequence:

1. **Explore:** Call all six agents in parallel (`asyncio.gather`) to gather exploratory evidence. Evidence is created with `hypothesis_id=None` and stored in `incident.exploratory_evidence`.

2. **Generate Hypotheses:** Call the LLM with exploratory evidence summaries. The LLM returns a `GenerateHypothesesOutput` with a list of `HypothesisProposal` objects (statement + optional parent_id). Parent references are resolved by position — the first root hypothesis is the parent for any child whose `parent_id` doesn't match an existing hypothesis ID.

3. **Investigate (loop):** For each depth level up to `max_depth` (default 3):
   - Find unresolved hypotheses (status `proposed` or `investigating`).
   - **Gather targeted evidence:** For each unresolved hypothesis, pick the most relevant source via keyword heuristic (`_pick_source`), call the corresponding agent, and link the evidence to the hypothesis.
   - **Evaluate:** Batch all unresolved hypotheses into a single LLM call. The LLM returns `EvaluateHypothesesOutput` with one evaluation per hypothesis. Match evaluations to hypotheses by ID, falling back to position-based matching if the IDs don't match (mock scenario).
   - **Prune:** Call `incident.prune_refuted_branches()` to cascade-refute children of refuted hypotheses.
   - **Deepen:** For confirmed *leaf* hypotheses only (those with no children), call the LLM to generate child hypotheses. If no new children are generated, the loop converges.
   - Increment depth and save.

4. **Produce RCA:** Find the highest-confidence confirmed hypothesis. Walk its confirmed path to build the causal chain. Call the LLM to produce an `RCAOutput` (root cause summary, confidence, remediation action). Transition the Incident to `rca_produced` then `pending_approval`.

### Agent Protocols

Each agent is a callable protocol with a uniform signature:

```
async def __call__(
    natural_language: str,
    hypothesis_id: str | None = None,
    extra_context: dict | None = None,
) -> Evidence
```

Six agents: MetricsAgent, LogsAgent, TraceAgent, KubernetesAgent, DeploymentAgent, KnowledgeAgent. Each maps 1:1 to an observability source. MCP is an implementation detail hidden behind the protocol.

### Source Routing Heuristic

Targeted evidence gathering uses a keyword heuristic (`_pick_source`) to route a hypothesis to the most relevant agent:

- `deploy`, `release`, `rollout`, `commit`, `config change` → DeploymentAgent
- `log`, `error`, `exception`, `crash` → LogsAgent
- `trace`, `span`, `latency`, `bottleneck`, `slow` → TraceAgent
- `pod`, `container`, `node`, `restart`, `crashloop`, `oom` → KubernetesAgent
- `runbook`, `procedure`, `documentation`, `known issue` → KnowledgeAgent
- Default → MetricsAgent (Prometheus)

### LLM Provider Interface

Single-method protocol:

```
async def generate_structured(
    prompt: str,
    output_schema: type[BaseModel],
    system_prompt: str = "",
    max_retries: int = 2,
) -> BaseModel
```

The `MockLLMProvider` implementation stores a queue of responses per schema type. Each `generate_structured` call pops and returns the next response. This supports multiple calls to the same schema (e.g., two `_deepen` calls both needing `DeepenHypothesesOutput`).

### Structured Output Models

Four Pydantic models define the LLM's output contract:

- `GenerateHypothesesOutput` — `hypotheses: list[HypothesisProposal]` where each proposal has `statement`, `parent_id` (nullable), and `rationale`
- `EvaluateHypothesesOutput` — `evaluations: list[HypothesisEvaluation]` where each evaluation has `hypothesis_id`, `status` (confirmed|refuted), `confidence` (0.0–1.0), and `reasoning`
- `DeepenHypothesesOutput` — `child_hypotheses: list[HypothesisProposal]` with child hypotheses that drill into confirmed parents
- `RCAOutput` — `root_cause_summary`, `confidence`, `remediation_action`

### Progressive Context Selection

Each LLM call receives only the data it needs. The `prompts.py` module builds prompts with targeted context:

| Call | Context |
|---|---|
| Generate hypotheses | Alert labels + exploratory evidence summaries |
| Evaluate hypotheses | Hypothesis statements + linked evidence summaries (batch) |
| Deepen hypotheses | Confirmed hypothesis + ancestor chain + evidence summaries |
| Produce RCA | Confirmed path + all evidence summaries |

The `raw_payload` field on Evidence is never sent to the LLM.

### Graceful Degradation

The `_safe_call` method wraps every agent call. If an agent raises an exception, it returns an `Evidence` object with `summary="Error: <details>"` and the error in `raw_payload`. The investigation continues. The LLM sees the error evidence during evaluation and can reason about data gaps.

### Leaf-Only Deepening

The `_phase_investigate_hypotheses` loop filters confirmed hypotheses to only those without children (`leaves = [h for h in confirmed if not incident.get_children(h)]`). This prevents re-deepening a hypothesis that was deepened in a previous iteration. If a hypothesis has children, it's already been explored; the children are the new frontier.

### Repository

The `IncidentRepository` protocol has three methods: `get(id)`, `save(incident)`, `list_active()`. The `InMemoryIncidentRepository` is a dict-backed implementation for MVP and tests. The Coordinator saves the Incident after each step, so a crash mid-investigation preserves all progress.

## Testing Decisions

### Primary Seam

The `Coordinator.run(incident_id)` method is the single entry point for all tests. Every test creates an Incident, saves it to the repository, configures mock LLM and mock agent responses, and calls `run()`. The test asserts the final Incident state and the RCA projection.

### Secondary Seams

- Agent protocols — each is a callable; `MockAgent` returns pre-built Evidence
- `LLMProvider.generate_structured()` — `MockLLMProvider` returns queued Pydantic objects
- `IncidentRepository` — `InMemoryIncidentRepository` with `save_count` for assertions

### What Makes a Good Test

Tests exercise the Coordinator's mechanics, not the LLM's judgment. They verify:
- The right agents are called in the right order
- LLM outputs are correctly applied to the Incident (hypotheses added, confirmed/refuted, pruned)
- The full lifecycle completes: `open → investigating → pending_approval`
- Error paths are handled: agent failure, all agents fail, no confirmed hypotheses
- The Incident is saved after each step

### Test Coverage

`tests/test_coordinator.py` — 9 tests:
- `test_full_happy_path` — two hypotheses, one confirmed, one refuted, converges
- `test_exploratory_evidence_gathered` — all six sources produce evidence
- `test_hypothesis_generation` — parent-child tree structure with parent_id resolution
- `test_hypothesis_evaluation` — single hypothesis confirmed with confidence
- `test_pruning_refuted` — parent refuted, children cascade-refuted
- `test_agent_failure_graceful` — one agent fails, five succeed, investigation continues
- `test_all_agents_fail` — all agents fail, error evidence produced, RCA still generated
- `test_saves_after_each_step` — repository save count increases after each phase
- `test_no_confirmed_hypotheses` — all hypotheses refuted, RCA with "no findings"

Plus `demo()` — a full integration scenario with mock LLM and mock agents that traces the investigation lifecycle from alert to resolved RCA.

### Prior Art

The `demo()` function in `tests/test_domain.py` (Phase 1) established the pattern of a single function that exercises the full lifecycle with assertions. The Phase 2 `demo()` in `tests/test_coordinator.py` follows the same pattern but drives the lifecycle through the Coordinator rather than manual method calls.

## Out of Scope

- MCP server implementations (Prometheus, Loki, Tempo, Kubernetes, GitHub, RAG)
- Real LLM provider implementations (PydanticAI, OpenAI, Claude)
- Agent implementations (the actual NL→PromQL→MCP→Evidence pipeline)
- Scheduler (async worker pool, concurrency cap, queue management)
- Alert Receiver (Alertmanager webhook, label-overlap grouping)
- Memory archiver (Incident → ResolvedIncident snapshot)
- Database persistence (PostgreSQL, SQLite)
- Event bus (domain events, pub/sub)
- LangGraph workflow definition
- Human approval workflow (the remediation gate is in the domain model, but the UI/API for it is out of scope)

## Further Notes

- The keyword heuristic in `_pick_source` is deliberately simple. A production system would replace it with an LLM call: "which observability source is most relevant for this hypothesis?" The heuristic exists so the Coordinator can be tested without an additional LLM round-trip.
- The `_resolve_parent_refs` method handles the case where the LLM returns placeholder parent IDs (e.g., "will-be-set" in mock scenarios). In production, the LLM prompt includes actual hypothesis IDs, and the LLM returns them correctly. The fallback is a safety net.
- The `_find_evaluation` position-based fallback exists for mock testing. In production, the LLM returns the actual hypothesis IDs from the prompt, so the ID-based match always succeeds.
- The batch evaluation in `_evaluate_all` combines all unresolved hypotheses into one LLM call. This is more efficient than one call per hypothesis and allows the LLM to compare hypotheses against each other.
- The `max_depth` parameter (default 3) prevents infinite deepening. A hypothesis chain of "service is slow → DB is slow → connection pool exhausted → config change removed timeout" is 4 levels deep. The default of 3 catches the first three levels; the fourth requires a second investigation pass or a higher max_depth config.
